Description
The init function in LockquidityVault can be called by any address with any token parameter. While the LockquidityFactory deploys and initializes the vault atomically in its constructor, if the vault contract is deployed independently or the factory deployment fails partway, the init function remains vulnerable to front-running.

function init(address token) public {
    require(!isInitialized);
    _token = IERC777(token);
    isInitialized = true;
}
An attacker monitoring the mempool could front-run the legitimate initialization with a malicious token address. Once initialized, the token cannot be changed. The vault would then operate with an attacker-controlled token, potentially redirecting all sweep operations to benefit the attacker.

## Developer Response & Architectural Context

This behavior is an **accepted and mitigated design choice** of the deployment setup.

### 1. Atomic Initialization in Factory Constructor
The `LockquidityVault` is designed to be deployed exclusively through the `LockquidityFactory` contract. In the factory's constructor, the vault is created and immediately initialized in the exact same execution frame:
```solidity
vault = new LockquidityVault();
token = new LockquidityToken(...);
vault.init(address(token));
```
Because these calls occur atomically within the constructor transaction, there is **no temporal gap** between the vault's deployment and its initialization. An attacker cannot inject a transaction to front-run `init()` because the contract does not yet exist on-chain before this block executes.

### 2. Already Deployed and Initialized
The vault and factory are already deployed on Arbitrum L2, and the initialization has been successfully completed. Because the initialization is a one-time operation (`require(!isInitialized)`), it is permanently locked and cannot be altered or hijacked.
