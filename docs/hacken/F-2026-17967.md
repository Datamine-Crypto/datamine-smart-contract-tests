Description
In ArbiFluxToken and LockquidityToken, getMintAmount computes the reward as amount * blocksMinted * burnMult * timeMult / divisors, applying both multipliers as scalars read from current state instead of integrating them over the accrual window.

function getMintAmount(address targetAddress, uint256 targetBlock) public view returns(uint256) {
    // ...
    uint256 blocksMinted = targetBlock.sub(targetAddressLock.lastMintBlockNumber);
    uint256 blocksMintedByAmount = amount.mul(blocksMinted);
    uint256 burnMultiplier = getAddressBurnMultiplier(targetAddress);
    uint256 timeMultipler = getAddressTimeMultiplier(targetAddress);
    uint256 fluxAfterMultiplier = blocksMintedByAmount.mul(burnMultiplier).div(_percentMultiplier).mul(timeMultipler).div(_percentMultiplier);
    // ...
}
getAddressTimeMultiplier derives its value from block.number, not targetBlock, and getAddressBurnMultiplier reads the current burnedAmount and globalRatio; both are then multiplied against every block in the window, including early blocks that accrued at a lower multiplier. Since burnToAddress writes neither blockNumber nor lastMintBlockNumber, it does not trip the preventSameBlock(sourceAddress) guard on mintToAddress, so a burn and a mint in one transaction apply fresh burn weight to the whole window. The intended "lock longer earns up to 3x" bonus is a time-weighted integral, whereas the implementation computes multiplier(now) * sum(blocks).

A locker who waits until the time multiplier caps at 3x and then mints one window applies 3x across the full duration, roughly 1.5x more than an incremental minter earns over the ramp. With no global emission cap, back-loading minters systematically over-extract relative to the documented schedule. No principal is at risk.

Remediation
Ensure each accrued block is rewarded at the multiplier that applied while it was earned, rather than at the current-state multiplier, so that delaying a mint or back-loading a burn cannot retroactively uplift earlier blocks. If the current behavior is intended, document the mint-time evaluation and its distributional effect explicitly.

function test_time_multiplier_backdated_over_whole_window() public {
    _lock(alice, L);
    _lock(dave, L);

    // Alice mints each block, tracking the ramp.
    for (uint256 e = 1; e <= RAMP; e++) {
        vm.roll(START + e);
        vm.prank(alice);
        arbi.mintToAddress(alice, alice, START + e);
    }

    // Dave takes the whole window in one mint at the 3x cap.
    assertEq(arbi.getAddressTimeMultiplier(dave), 30000, "dave at 3x cap"); // 30000 = 3.0x
    vm.prank(dave);
    arbi.mintToAddress(dave, dave, START + RAMP);

    uint256 aliceMinted = arbi.balanceOf(alice);
    uint256 daveMinted = arbi.balanceOf(dave);

    assertTrue(daveMinted > aliceMinted, "back-loading did not over-earn");
    uint256 ratioPct = daveMinted * 100 / aliceMinted;
    assertTrue(ratioPct >= 148 && ratioPct <= 150, "~1.49x over-emission");
}

function test_burn_multiplier_backdated_via_burn_then_mint_one_block() public {
    _lock(mallory, 1e18);
    _lock(carol, 4e18); // passive: makes mallory's burn worth exactly 6x

    vm.roll(START + RAMP); // age the position, no minting

    assertEq(arbi.getAddressBurnMultiplier(mallory), 10000, "1x before burn"); // 10000 = 1.0x
    uint256 fair = arbi.getMintAmount(mallory, START + RAMP);

    // Same block: burn spikes the multiplier (burnToAddress has no preventSameBlock)
    _burnSelf(mallory, 1e18);
    assertEq(arbi.getAddressBurnMultiplier(mallory), 60000, "6x after last-block burn"); // 60000 = 6.0x

    // Same already-accrued window is now worth 6x.
    uint256 gamed = arbi.getMintAmount(mallory, START + RAMP);
    assertEq(gamed, fair * 6, "burn back-dated 6x onto the whole window");

    vm.prank(mallory);
    arbi.mintToAddress(mallory, mallory, START + RAMP);
    assertEq(arbi.balanceOf(mallory), gamed, "6x paid out from one-block burn-then-mint");
}

## Developer Response & Architectural Context

This behavior is an **intentional design choice** designed to optimize gas efficiency and introduce favorable economic incentives for validators.

### 1. Gas Optimization and O(1) Scalability
Calculating time-weighted or checkpointed multipliers block-by-block would require loop iterations or complex contract checkpointing storage writes. 
* On Ethereum Mainnet (L1) and rollup chains (L2), loop-based historical calculations consume substantial gas, which could easily exceed the value of the validator's accrued mint rewards.
* Computing the multiplier as a simple, constant-time `O(1)` evaluation at the moment of minting avoids loop execution, keeping transaction fees as low as possible for all users.

### 2. Retroactive Burn Incentives ("Supercharging")
Allowing retroactive multipliers is a core game-theoretic mechanic of the ecosystem. It enables validators to accumulate rewards over time and then execute a single large burn to "supercharge" their entire pending block window. This immediate payoff provides a strong psychological and economic incentive for validators to commit capital to burning.

### 3. Verification in Unit Tests
This behavior is explicitly covered and expected in our test suites:
* `Should allow multiplier retroactivity / supercharging in the same block` in both `FluxTokenAttackTests.ts` and `LockTokenAttackTests.ts` verifies and guards this dynamic.

### 4. Contract Immutability
The deployed contracts are completely decentralized and immutable. This retroactive multiplier mechanism has operated securely and transparently in production for over 5 years (on L1 FLUX) and over 1 year and 262 days (on L2 LOCK).
