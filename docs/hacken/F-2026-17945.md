Description
In LockquidityVault, the sweep function is external and permissionless, guarded only by a check that the vault is initialized. It reads the vault's full LOCK balance and routes it through zap, which sizes and executes a swap and liquidity deposit against live pair reserves in the same call frame, with no trusted price reference and no slippage protection.

function zap(address _tokenA, address _tokenB, uint256 _amountA) internal {
    // ...
    (uint256 reserve0, uint256 reserve1,) = IUniswapV2Pair(pair).getReserves();
    // swapAmount derived from live reserves in the same frame
    swapAmount = getSwapAmount(reserve0, _amountA);
    _swap(_tokenA, _tokenB, swapAmount);
    _addLiquidity(_tokenA, _tokenB);
}

function _swap(address _from, address _to, uint256 _amount) internal {
    // ...
    IUniswapV2Router(ROUTER).swapExactTokensForTokens(_amount, 1, path, address(this), block.timestamp);
}
The swap accepts amountOutMin of 1, and the liquidity add passes both minimums as 0, so any output ratio is accepted. Because the swap size is derived from the same reserve an attacker just manipulated, inflating the LOCK reserve makes the vault swap more LOCK at the worse price, amplifying the loss. The caller controls timing and transaction context, so the attacker originates a single atomic transaction that skews the pool, calls sweep, then restores the pool and repays a flash loan, capturing the price-impact differential. Arbitrum's lack of a public mempool provides no mitigation since no front-running of a victim is required. The deadline value of the current block timestamp always satisfies the router check and adds no protection.

Since the vault accumulates all burned LOCK with no withdrawal path, the extracted value is irrecoverable and the leak repeats on every accrual and sweep cycle. Severity escalates toward catastrophic when the vault balance is large relative to a thin pool, where a single attack can remove more than a tenth of the swapped value.

Remediation
Enforce real slippage bounds instead of the current fixed floors of 1 and 0. Two options:

Require the caller to pass a minimum WETH output and minimum LP amount, and revert when either is unmet.
Derive those minimums on-chain from a manipulation-resistant price such as a time-weighted average or an external oracle, and bound the allowed deviation.
Restricting sweep to an authorized keeper further removes the attacker's control over timing.

## Developer Response & Architectural Context

This behavior is a known design constraint of the decentralized, permissionless architecture of the Lockquidity vault.

### 1. Rationale for Permissionless Design
To maintain the protocol's strict definition of absolute decentralization ("no admin keys, no DAO, no servers/central entities"), the `sweep()` function was designed to be permissionless. Anyone can call it at any time to execute the liquidity injection without relying on a centralized keeper bot.

### 2. Economic Mitigations & Friction
While the sandwich vector is theoretically possible if the vault holds a very large LOCK balance, it is mitigated by several factors in practice:
* **Uniswap Trading Fees**: An attacker must perform both an entry swap and an exit swap, incurring Uniswap's 0.3% fee twice (0.6% total pool trading friction) in addition to Arbitrum gas costs.
* **Frequent Sweeps**: In production, the vault is swept by a bot every few hours. This keeps the accumulated vault amounts very small relative to the Uniswap pool size.
* **Negligible Profit**: Due to the small swept amounts, any potential slippage profit from a sandwich attack is extremely low—on the order of a few cents. This is too small to motivate rational actors when transaction and swap fee overhead are considered.
* **Decentralized Sweeping Incentive**: Having third-party bots trigger the sweep is a deliberate design choice. If external bots are incentivized to call `sweep()`, it decentralizes the sweeping mechanics further (which is a core goal). The protocol is willing to pay a small premium (in the form of minor slippage) to achieve this fully decentralized, serverless automation.
* **Permanently Locked LP**: All Uniswap LP tokens generated during the `sweep()` are minted directly to `address(this)` (the vault contract). Since the vault contains no transfer, approval, or withdrawal logic for LP tokens, these LP tokens are permanently locked (effectively burned) inside the protocol, securing long-term liquidity depth.


### 3. Contract Immutability
The `LockquidityVault` contract is deployed as an immutable protocol on Arbitrum (L2) with no admin controls, owner keys, or upgrade path.
