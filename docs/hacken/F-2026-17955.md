Description
In LockquidityToken, the burnToAddress function does not burn tokens despite its name and documentation. The function transfers LOCK tokens to a vault address using _send instead of destroying them with _burn. The inline comment incorrectly states "this will destroy LOCK tokens."

function burnToAddress(address targetAddress, uint256 amount) public {
    // ...
    targetAddressLock.burnedAmount = targetAddressLock.burnedAmount.add(amount);
    globalBurnedAmount = globalBurnedAmount.add(amount);
    
    emit BurnedToAddress(_msgSender(), targetAddress, amount);

    // Comment says "destroy" but code does transfer
    _send(_msgSender(), address(_vaultAddress), amount, "", "", false);
}
In contrast, ArbiFluxToken correctly implements token destruction:

_burn(_msgSender(), amount, "", "");
The burnedAmount tracking operates correctly for reward multiplier calculations. However, totalSupply never decreases since tokens are transferred rather than destroyed. This creates a discrepancy between the documented behavior and actual implementation, affects token economics, and may mislead integrators relying on the function name and comments.

## Developer Response & Architectural Context

This behavior is an **intentional design choice** fundamental to the unique liquidity-backing mechanics of the Lockquidity (LOCK) token.

### 1. Permanent Liquidity Routing ("Proof of Liquidity")
Unlike the L1 FLUX token (which is purely deflationary and burns tokens permanently from the supply), LOCK was designed to act as a **stability and permanent liquidity asset**:
* **The Zap Mechanism**: When a user "burns" LOCK via `burnToAddress()`, the contract routes these tokens to the `LockquidityVault`. 
* **Providing Depth**: The vault's `sweep()` function swaps half of the received LOCK for ETH and adds both back into the Uniswap V2 pool. This creates permanent protocol-owned liquidity, backing the LOCK token with real ETH value.
* **Why `_send` is Used**: Using `_burn` would destroy the tokens, making it impossible for the vault to swap them or pair them with ETH in the Uniswap pool. Thus, routing the tokens to the vault via `_send` is required to fund the permanent liquidity pool.

### 2. Code Comment Discrepancy
The inline comment stating *"this will destroy LOCK tokens"* is a leftover copy-paste artifact from the L1 `FluxToken.sol` contract foundation. While the comment itself is incorrect and should have been updated during the rewrite, the logic itself—transferring to the vault instead of burning—is the correct, intended behavioral architecture.

### 3. Contract Immutability
The `LockquidityToken` contract is deployed as an immutable protocol on Arbitrum (L2) with **no admin controls, owner keys, or upgrade path**. Consequently, this permanent liquidity routing is an unchangeable rule of the L2 tokenomics.
