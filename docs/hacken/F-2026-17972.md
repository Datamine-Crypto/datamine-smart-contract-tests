Description
The preventSameBlock modifier enforces that lock, unlock, and mintToAddress cannot be called in the same block by checking blockNumber and lastMintBlockNumber. However, the unlock function does not update either timestamp field after execution.

function unlock() preventRecursion preventSameBlock(_msgSender()) requireLocked(_msgSender(), true) public {
    AddressLock storage senderAddressLock = addressLocks[_msgSender()];
    uint256 amount = senderAddressLock.amount;
    senderAddressLock.amount = 0;
    // blockNumber and lastMintBlockNumber are NOT updated
    globalLockedAmount = globalLockedAmount.sub(amount);
    globalBurnedAmount = globalBurnedAmount.sub(senderAddressLock.burnedAmount);
    IERC777(_token).send(_msgSender(), amount, "");
}
If a user locked at block N and unlocks at block M, blockNumber remains N. A second transaction in block M can call lock because the check blockNumber != block.number passes (N != M).

Remediation
Update blockNumber to the current block in unlock to maintain the same-block protection invariant:

function unlock() preventRecursion preventSameBlock(_msgSender()) requireLocked(_msgSender(), true) public {
    AddressLock storage senderAddressLock = addressLocks[_msgSender()];
    uint256 amount = senderAddressLock.amount;
    senderAddressLock.amount = 0;
    senderAddressLock.blockNumber = block.number;  // Add this line

## Developer Response & Architectural Context

This behavior is an **intentional design choice** designed to support user convenience (unlocking and immediately re-locking) while maintaining absolute system safety.

### 1. Enabling Single-Block Re-Locking and Test Coverage
If a validator wants to update their delegated minter address or modify their locked amount, they must call `unlock()` and then `lock()`. 
* **The Single-Block UX**: Allowing a user to `unlock()` and immediately `lock()` again in the same block M is a beneficial design feature. It lets users reconfigure their positions without waiting for the next block to execute, saving gas and transaction overhead.
* **Why This is Safe**: Since the lock state is updated in the subsequent `lock()` call, the new `blockNumber` is set to block M. As a result, the user is still correctly prevented from calling `mintToAddress()` in block M (since the new `blockNumber == M` fails the `preventSameBlock` check).
* **Test Coverage**: We explicitly test the security and state persistence of unlock/re-lock sequences in our test suites:
  * `should not be possible to mint tokens for a past lock period after re-locking` (in `FluxTokenAttackScenariosTests.ts` and `LockTokenAttackScenariosTests.ts`) ensures that re-locking correctly updates block tracking and prevents claiming historical rewards.
  * `Should preserve burned amount across unlock/re-lock cycles (no free multiplier reset)` (in `FluxTokenAttackTests.ts` and `LockTokenAttackTests.ts`) validates correct state restoration across these transition cycles.


### 2. Multi-Unlock Prevention
Allowing the block tracking to remain unmodified on `unlock()` does not introduce any double-spend or double-unlock vulnerabilities:
* `unlock()` is protected by the `requireLocked(_msgSender(), true)` modifier, which asserts that `amount > 0`.
* Since `unlock()` immediately sets `amount = 0`, any secondary attempt to call `unlock()` in the same block will revert due to the zero-balance requirement, ensuring double-unlocking is structurally impossible.

### 3. Contract Immutability
The contracts are deployed as decentralized, immutable protocols on-chain, and this transition logic has operated securely and transparently in production.
