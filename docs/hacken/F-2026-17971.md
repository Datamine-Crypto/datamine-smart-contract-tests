Description
In LockquidityToken and ArbiFluxToken, the getMintAmount function calculates minting rewards using several scaling divisions. The order of operations can truncate fractional rewards to zero for small lock amounts or short minting intervals.

uint256 blocksMintedByAmount = amount.mul(blocksMinted);
uint256 fluxAfterMultiplier = blocksMintedByAmount.mul(burnMultiplier).div(_percentMultiplier).mul(timeMultipler).div(_percentMultiplier);
uint256 actualFluxMinted = fluxAfterMultiplier.div(_mintPerBlockDivisor);
With _percentMultiplier = 10000 and _mintPerBlockDivisor = 10^8, the final division requires fluxAfterMultiplier >= 10^8 for a non-zero mint amount. At minimum intended multipliers, this requires amount * blocks >= 10^8 wei. Earlier divisions by _percentMultiplier discard precision before the final mint divisor is applied, so small valid locks can accumulate less than one whole reward unit for a given mint window and receive no LOCK rewards. The user must wait longer or lock more tokens to cross the integer threshold, while gas is still spent on failed zero-mint attempts.

Additionally, early divisions discard precision that could be preserved by reordering operations. The current formula performs two divisions before the final scaling, each truncating intermediate results. Multiplying all numerators first and dividing once at the end would retain maximum precision.

Remediation
Reorder arithmetic operations to preserve precision by multiplying before dividing:

uint256 blocksMintedByAmount = amount.mul(blocksMinted);
uint256 numerator = blocksMintedByAmount.mul(burnMultiplier).mul(timeMultipler);
uint256 denominator = _percentMultiplier.mul(_percentMultiplier).mul(_mintPerBlockDivisor);
uint256 actualFluxMinted = numerator.div(denominator);
Consider adding a minimum lock amount or minimum mint interval check to prevent dust locks from producing zero rewards.


## Developer Response & Architectural Context

This behavior is an **accepted architectural trade-off** in the protocol's mathematical design.

### 1. Overflow Prevention
The smart contracts were developed in Solidity v0.6.9. At the time of design, performing multiple large multiplications (`amount * blocksMinted * burnMultiplier * timeMultiplier`) in a single step carried a significant risk of integer overflow (exceeding `uint256` max) for validators holding substantial balances over multi-year timelines. By performing step-wise intermediate divisions, the contract ensures that numbers stay within safe bounds, completely eliminating overflow risk.

### 2. State Bloat & Dust Mitigation
Discarding fractional precision for extremely small "dust" positions (e.g., locking negligible amounts of wei or attempting to mint after only a few seconds) is a deliberate mechanism to prevent network spam and state bloat. 
* **The Mathematical Threshold**: For a non-zero reward, the division requires `amount * blocks >= 10^8` (wei-equivalent units). Since 1 token (LOCK or ArbiFLUX) is $10^{18}$ wei, a standard lock of even **1 token** ($10^{18}$ wei) clears this threshold on the very first block ($10^{18} \cdot 1 \gg 10^8$).
* **Real-World Metrics**: A lock must be less than $0.0000000001$ tokens ($10^8$ wei) to experience truncation. In the actual production ecosystem:
  * **LOCK Current Supply**: 30,131.51096831 LOCK / $71,326.96 USD
  * **ArbiFLUX Available Liquidity**: 60,305.43 ArbiFLUX
  Normal user locks are typically in the hundreds or thousands of tokens, which sit 12 to 15 orders of magnitude above this dust limit. Therefore, this precision loss has zero impact on any legitimate validator.
* It discourages users from wasting gas on economically sub-optimal operations.


### 3. Contract Immutability
The deployed smart contracts are completely decentralized and immutable, with **no admin keys or upgrade path**. This precision behavior is a permanent rule of the ecosystem, and has successfully operated without issue for 5+ years on Ethereum L1 and over 1 year and 262 days on Arbitrum L2.
