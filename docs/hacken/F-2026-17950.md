Description
In ArbiFluxToken, every block-based constant is calibrated to a "1 block = 15 seconds" assumption inherited from the pre-Merge Ethereum design, including the reward start delay, the maximum time-bonus window, the base per-block emission rate, and the failsafe window. These values feed getAddressTimeMultiplier and the emission math in getMintAmount. The same constants and calibration are reused unchanged by the LOCK layer in LockquidityToken, so the deviation applies to the shared reward engine, not to a single token.

function getAddressTimeMultiplier(address targetAddress) public view returns(uint256) {
    // ...
    uint256 targetBlockNumber = targetAddressLock.blockNumber.add(_startTimeReward);
    // ...
    uint256 blockDiff = block.number.sub(targetBlockNumber).mul(_targetBlockMultiplier).div(_maxTimeReward).add(_percentMultiplier);
    uint256 timeMultiplier = Math.min(_maxTimeMultiplier, blockDiff);
    return timeMultiplier;
}
On Arbitrum, block.number tracks the L1 block number estimate, which advances at the roughly 12-second Ethereum cadence, not an L2 transaction counter. Post-Merge L1 blocks are about 12 seconds rather than the assumed 15, so the block height advances about 1.25x faster per unit real time. The emission rate therefore over-delivers by roughly 25%, while the bonus ramp reaches its thresholds sooner in real time: the time bonus starts after about 19.2 hours instead of 24, and the maximum 3x bonus is reached after about 22.4 days instead of 28. All governing constants are immutable or constant with no setter, so the deviation from the documented 24-hour and 28-day schedule is permanent.

There is no principal loss and no cross-user theft; the deviation is confined to the protocol's own emission rate and bonus timing, and it affects all participants uniformly.

Remediation
Recompute the reward start delay, the maximum time window, the failsafe duration, and the per-block emission against the actual Arbitrum block cadence in both ArbiFluxToken and LockquidityToken.

Alternatively, migrate the schedule to block.timestamp, which tracks wall-clock time far better than block.number over multi-day windows on L2.

If the constants are already deployed and immutable, document the true real-time schedule for users.


## Developer Response & Architectural Context

This behavior is a known constraint of using block-based timing on Ethereum and Arbitrum L2, and is an accepted aspect of the protocol's design.

### 1. Parity with L1 FLUX
The core parameters (24-hour reward start delay, 28-day multiplier ramp) were originally calibrated for L1 FLUX in 2020 using the pre-Merge Ethereum block times of 15 seconds. For the L2 deployments (ArbiFLUX and LOCK), maintaining exact parity in constant parameters was chosen to keep ecosystem calculations, documentation, and logic consistent across L1 and L2.

### 2. Arbitrum's block.number Cadence
On Arbitrum, `block.number` returns the L1 block number estimate rather than the L2 transaction counter. While the shift from 15-second pre-Merge blocks to 12-second post-Merge blocks means blocks advance ~1.25x faster, this is a standard chain-wide L1 timing change.
* **Effect on Emission**: LOCK and ArbiFLUX emission rates are ~25% higher relative to wall-clock time.
* **Effect on Bonus Timing**: The 24-hour time bonus threshold starts at ~19.2 hours, and the 28-day 3x cap is reached in ~22.4 days.

### 3. Uniformity and Immutability
This timing shift affects all protocol participants uniformly, ensuring that no individual user can gain an unfair advantage or exploit other users. 

Since the deployed contracts are fully decentralized, immutable, and have **no admin keys or upgrade path**, these block-based timing parameters are permanent. The community and frontend dashboards are fully aware of and have adapted to this 12-second block estimation schedule, which has successfully run for over 1 year and 262 days on Arbitrum.
