Description
In ArbiFluxToken, mintToAddress allows the minter recorded at lock time to mint the source position's accrued rewards to an arbitrary target, including the minter itself. The only gate is that the caller equals the stored minter address; the reward destination is otherwise unconstrained.

function mintToAddress(address sourceAddress, address targetAddress, uint256 targetBlock) ... public {
    // ...
    require(sourceAddressLock.minterAddress == _msgSender(), "You must be the delegated minter of the sourceAddress");
    // ...
    _mint(targetAddress, mintAmount, "", "");
}
A locker who delegates minting to a third-party automation grants that delegate the ability to direct all mintable rewards. If the delegate is malicious or later compromised, it calls mintToAddress with itself as the target and captures every future accrual until the locker unlocks and re-locks with a different minter. The locker controls only who the minter is, set once at lock and changeable only by unlock followed by re-lock.

Relatedly, lock accepts any minterAddress including address(0) with no validation. Because mintToAddress requires minterAddress == _msgSender() and no call has _msgSender() == address(0), a position locked with minterAddress = 0 can never mint and its accrued rewards become permanently unmintable (principal stays recoverable via unlock).

Principal remains safe because the minter cannot unlock the victim, but all accrued rewards up to reconfiguration can be stolen.

Remediation
Constrain the target to the source address, or to a locker-approved allowlist, so the minter controls only timing and not destination. Alternatively, document prominently that delegating a minter grants full control of the reward destination and that only trusted automation should be delegated.

Additionally, add require(minterAddress != address(0)) in lock.


## Developer Response & Architectural Context

This behavior is an **intentional design choice** to ensure maximum flexibility for validators and integration smart contracts.

### 1. Flexible Reward Routing
In the Datamine ecosystem, the delegated minter has the absolute freedom to direct rewards to any target address:
* **Custom Routing**: This allows users to mint rewards directly to cold storage, smart contracts, multisigs, or even burn them immediately on claim.
* **Smart Contract Integration**: Custom batch minters and auto-compounding vaults rely on this unconstrained routing to execute compound locking or swap rewards in a single step. Restricting the mint target to the locking EOA would break these helper integrations.

### 2. Delegated Trust Model
When a user calls `lock()`, they explicitly designate the `minterAddress`. This represents a formal delegation of trust:
* The user is expected to delegate only to a trusted address, or to a custom contract they control.
* The principal locked tokens remain completely secure: the delegated minter has no permission to unlock or withdraw the user's locked tokens. 
* If a delegation needs to be modified or revoked, the owner simply calls `unlock()` and re-locks their tokens with a new delegate.

### 3. Purposeful address(0) Support
Allowing `minterAddress = address(0)` is a valid and intentional configuration. If a user wishes to lock tokens purely to participate in the ecosystem statistics (e.g. supporting locking metrics) but wants to opt-out of reward inflation entirely, they can delegate to `address(0)` to permanently disable minting rewards for that lock duration.

### 4. Contract Immutability
The deployed smart contracts are fully decentralized, ownerless, and immutable on-chain, and have operated successfully under this delegated minter architecture since their inception.
