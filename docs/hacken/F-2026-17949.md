Description
The Flux, ArbiFluxToken, and LockquidityToken contracts return or mint tokens through ERC-777 paths that call the recipient reception hook with the ack flag hardcoded to true. When the recipient is a contract with no registered ERC-1820 implementer, _mint and send revert on the check that forbids a contract recipient. Most contracts (multisigs, vaults, routers, exchange deposit addresses) never register one.

On the bridge path, bridgeMint forwards to _mint while the gateway redeems the deposit's retryable ticket, so the revert blocks L2 finalization; the ticket expires in about a week and the escrowed L1 tokens stay locked with no L2 counterpart.

function bridgeMint(address account, uint256 amount) external virtual override onlyGateway {
    _mint(account, amount, '', '');
}
On the token path, a contract can lock (the operatorSend recipient is the self-registered token contract), but unlock returns principal via send with requireReceptionAck = true, whose recipient is now the contract locker:

function unlock() /* ... */ public {
    // ...
    IERC777(_token).send(_msgSender(), amount, "");
}
_callTokensReceived finds no implementer and reverts, so a hookless contract locker reverts on every unlock. If it cannot register an implementer afterward, its principal is permanently unrecoverable; the same applies to mintToAddress minting to a hookless target. Externally owned accounts are unaffected.

Remediation
For the bridged L2 token, prefer a plain ERC-20 so the mint path cannot revert on contract recipients, per Arbitrum's L2GatewayToken guidance. For unlock and mintToAddress, return funds with a non-ack transfer or restrict participation to ERC-777-aware recipients. At minimum, document the recipient-hook requirement for contract integrators.


## Developer Response & Architectural Context

This behavior is an **accepted risk** stemming from the protocol's reliance on the ERC-777 token standard.

### 1. Context and Arbitrum Bridge Frontend Restrictions
This protocol was designed and deployed before Smart Accounts became prevalent. For standard operations:
* The Arbitrum bridge frontend is built to expect and handle Externally Owned Accounts (EOAs). If EOA verification is active, the frontend itself will throw an error and prevent bridging from a smart contract address that does not support the bridge.
* If a custom smart contract wants to utilize the Arbitrum bridge to transfer tokens, it **must** register an implementer for `ERC777TokensRecipient` via the ERC-1820 registry to ensure compatibility.

### 2. Compatibility Layer
To support Smart Accounts (like MetaMask's new default smart accounts) that do not implement the ERC-1820 registry by default, the protocol utilizes wrapper or helper contracts to bridge the gap. For any custom contract integration, registering the appropriate ERC-1820 interface remains a prerequisite to ensure compatibility with our ERC-777 token rules.
